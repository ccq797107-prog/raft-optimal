# 云上快速部署测试（华为云 3 地域真实集群）

一份从零到出结果的「照抄即可」指南：**改 IP → 一键拉起集群 → 跑读写 → 看 Global Leader**。
对应 docker 版的 `docker/快速部署测试.md`，但这里是**真实跨地域网络**（北京/上海/广州三台云主机），延迟不是 tc 模拟的，是真实骨干网 RTT。

拓扑（与 docker 版一致，3 域 × 3 节点）：


| 域        | 地域  | 机器  | 节点       | 端口                    |
| -------- | --- | --- | -------- | --------------------- |
| domain-a | 北京  | 1 台 | a1 a2 a3 | 7101-7103 / 8101-8103 |
| domain-b | 上海  | 1 台 | b1 b2 b3 | 同上                    |
| domain-c | 广州  | 1 台 | c1 c2 c3 | 同上                    |


所有命令都在**本地开发机（Mac）的项目根目录**执行，脚本通过 SSH 操控三台云主机。

只用到 2 个脚本：


| 脚本                        | 作用                       |
| ------------------------- | ------------------------ |
| `scripts/cloud-deploy.sh` | 编译、分发、起停集群、看状态、看日志       |
| `scripts/cloud-client.sh` | 从某个域发读/写、查 Global Leader |

## 零、换机器 / 换弹性 IP 时改哪里（必看）

IP 一共写在 **3 个文件**里，换 EIP 或换机器时三处都要对上：


| 文件                                  | 改什么              |
| ----------------------------------- | ---------------- |
| `config/cluster.huawei.json`        | 每个节点 4 类地址（见下）   |
| `scripts/cloud-deploy.sh` 的 `eip()` | 域字母 → EIP（SSH 用） |
| `scripts/cloud-client.sh` 的 `eip()` | 同上               |


`cluster.huawei.json` 里每个节点的地址含义（以北京 a1 为例）：

```json
{"id": "a1", "domainCode": "domain-a",
 "listenAddress":            "192.168.0.198:7101",   ← 本机私网IP:端口（同域节点互拨）
 "interDomainAddress":       "192.168.0.198:8101",   ← 本机私网IP:端口（缺省回退，不实际使用）
 "bindListenAddress":        "0.0.0.0:7101",         ← 不用改
 "bindInterDomainAddress":   "0.0.0.0:8101",         ← 不用改
 "publicListenAddress":      "1.92.115.7:7wo101",      ← EIP:端口（客户端重定向）
 "publicInterDomainAddress": "1.92.115.7:8101"}      ← EIP:端口（跨域节点互拨）
```

规则总结：

- **弹性 IP 变了**：改该机器 3 个节点的 `publicListenAddress` + `publicInterDomainAddress`，以及两个脚本里 `eip()` 对应行。
- **私网 IP 变了**（换机器才会）：改该机器 3 个节点的 `listenAddress` + `interDomainAddress`。
- 改完执行 `./scripts/cloud-deploy.sh deploy && ./scripts/cloud-deploy.sh restart` 生效。

当前三台机器：


| 域     | EIP           | 私网 IP         |
| ----- | ------------- | ------------- |
| a（北京） | 1.92.115.7    | 192.168.0.198 |
| b（上海） | 123.60.74.154 | 192.168.0.122 |
| c（广州） | 110.41.85.62  | 192.168.0.229 |

## 一、前置条件（每台机器一次性）

1. **SSH 免密**：本机能直接 `ssh root@<EIP>` 进三台机器。

```bash
ssh-copy-id root@1.92.115.7
ssh-copy-id root@123.60.74.154
ssh-copy-id root@110.41.85.62
```

> 用 .pem 密钥对或非 root 用户的话，所有脚本命令前加环境变量：
> `SSH_USER=ubuntu SSH_KEY=~/Downloads/xxx.pem ./scripts/cloud-deploy.sh ...`

1. **安全组**：每台机器放通 TCP 端口：
  - `8101-8103`（跨域 RPC）：来源 = 另外两台的 EIP（如北京放通 `123.60.74.154/32` 和 `110.41.85.62/32`）
  - `7101-7103`（客户端）：来源 = 你本地的出口 IP（测试图省事可临时 `0.0.0.0/0`，测完收紧）
  - `22`（SSH）：来源 = 你本地的出口 IP

> 当前 gRPC 是明文无鉴权，端口暴露公网只适合短期测试。

## 二、最短路径（一条命令出结果）

```bash
./scripts/cloud-deploy.sh all
```

这条命令依次做：交叉编译 linux 二进制 → scp 分发到三台机器的 `/opt/cd-raft/` → 每台后台启动本域 3 个节点 → 等 20s 选举收敛 → 打印 9 个节点状态 → 北京写入、上海/广州读出验证。

末尾看到这样即成功：

```
==> 1) 从北京(domain-a)写入  key=probe-...
[1/1] write winner=... index=1 result=probe-...=hello-from-beijing latency=...ms
==> 2) 从上海(domain-b)读取（验证跨域复制与重定向）
probe-...=hello-from-beijing
==> 跨域读写验证通过
```

之后也可以分步执行：

```bash
./scripts/cloud-deploy.sh deploy    # 只编译 + 分发（节点跑着也能执行，传完要 restart 才生效）
./scripts/cloud-deploy.sh start     # 启动 9 个节点（幂等，已运行的跳过）
./scripts/cloud-deploy.sh status    # 每台机器的进程 + 每个节点的角色/GL/任期/提交位点
./scripts/cloud-deploy.sh restart   # 重启（数据保留）
./scripts/cloud-deploy.sh stop      # 全部停止
./scripts/cloud-deploy.sh clean     # 停止 + 清空数据目录（回到全新集群）
./scripts/cloud-deploy.sh logs a2   # 跟踪某个节点的日志（Ctrl-C 退出）
```

## 三、跑读写（与 docker 的 client.sh 用法一致）

```bash
# 用法：./scripts/cloud-client.sh <a|b|c> <read|write> [条数] [key] [value]
./scripts/cloud-client.sh a write 10          # 从北京写 10 次（默认 key=foo value=bar）
./scripts/cloud-client.sh b read 10           # 从上海读 10 次
./scripts/cloud-client.sh c write 5 mykey hi  # 从广州写 5 次 mykey=hi

./scripts/cloud-client.sh gl                  # 当前 Global Leader 是谁、在哪个域
```

脚本会 SSH 到那个地域的机器、用机器上的 `cdraft-client` 发请求——**请求真正从那个域发起**，延迟就是真实的跨地域 RTT。逐条打印延迟，结尾给 `total / avg / min / max` 汇总。

> 细节：脚本发请求前会先问本机节点 GL 在哪。GL 恰好在本域（同机）时直接打 GL 的本地端口，避开「云主机访问自己 EIP 不通」（NAT 不回环）的坑；GL 在远端则正常走重定向。

### 查看跨域时延拓扑（RTT 矩阵）

拉取集群**自己实测**的跨域 RTT 矩阵（节点靠心跳/通告持续测量；GL 视图最全）。这正是代价模型和 Fast Return responder 选择所用的数据：

```bash
./scripts/cloud-deploy.sh rtt           # a/b/c 共识域矩阵
./scripts/cloud-deploy.sh rtt --with-d  # 顺带显示漂流域 d 的行
```

输出形如（单位 ms，往返 RTT，对角线 `~0`，缺测方向 `-`）：

```
from\to(ms)       a       b       c
a              ~0      26      36
b              24      ~0      28
c              38      28      ~0
```

本机直连 EIP 查询（与 `cdraft-mover` / `cloud-gl.sh` 同款），无需 SSH、无需先 deploy；首次运行会自动构建 `bin/cdraft-client`。

> **为什么默认看不到 d？** 共识域 a/b/c 的 RTT 是持续测量、常驻的；而漂流域 d 的延迟是**易逝**的——只有客户端 `-report-floating-latency` 上报，GL 端按 `floatingTelemetryTtlMillis`（默认 5s）过期。所以单独跑 `rtt`（或在 `cloud-client.sh d write` 跑完几秒后再跑）时，d 的延迟早已过期、不显示。`--with-d` 会先 SSH 到贵阳机器实测上报，再在 TTL 内立刻拉矩阵，这样就能看到 d 行。
>
> 同理：`d write` 能稳定走 Fast Return，靠的就是它在**同一个 SSH 会话**里先上报再写，保证写期间 telemetry 一直新鲜。

## 四、改代码 / 改配置后如何生效（必看）

二进制和配置都是部署时拷到机器上的，改完**必须重新分发 + 重启**：

```bash
# 改了 Go 代码（internal/、cmd/）
./scripts/cloud-deploy.sh deploy && ./scripts/cloud-deploy.sh restart

# 只改了 config/cluster.huawei.json（拓扑/功能开关）——同样两步，deploy 很快
./scripts/cloud-deploy.sh deploy && ./scripts/cloud-deploy.sh restart
```

> deploy 不需要先 stop：文件先传到 `.staging/` 再 `mv` 覆盖，正在运行的进程不受影响（它们继续用旧文件，restart 后才切新）。
>
> 改了持久化格式的话，用 `./scripts/cloud-deploy.sh clean` 从干净状态开始，避免新旧数据混淆。

## 五、功能开关（在 `config/cluster.huawei.json` 的 `features` 里）

```json
"features": {
  "fastReturnEnabled": true
}
```


| 开关                  | 作用                                                                  |
| ------------------- | ------------------------------------------------------------------- |
| `fastReturnEnabled` | 跨域写时，起源域的 Domain Leader 就近快速应答（≈1 个跨域 RTT）；关掉则等 GL 正常返回（≈2 个跨域 RTT） |


改完 `deploy + restart` 生效。

## 六、怎么解读结果

第 1 条总是偏高（冷连接 + 首次重定向发现 GL）；客户端会缓存 GL 地址，**从第 2 条起是稳态**。

**读**：由 Global Leader 服务，稳态延迟 ≈ 1 个 client↔GL 真实 RTT。


| client 域 与 GL 域 | 稳态读延迟                       |
| --------------- | --------------------------- |
| 同域（同机）          | ~1 ms                       |
| 跨域              | ≈ 该链路真实 RTT（京沪/京广约 25~40ms） |


**写**：`winner` 字段说明谁应答的：

- `domain-leader-fast-return`：起源域 ≠ GL 域且开了 Fast Return，≈ 1 个跨域 RTT；
- `global-leader`：起源域 = GL 域（或没开 Fast Return），等完整两域提交，≈ 2 个跨域 RTT。

例：GL 在北京 a2、从上海 `write`，关 Fast Return 时 ~68ms，开了之后应降到 ~35ms 上下（以实测为准，真实骨干网有抖动）。

## 七、故障 / 容错测试

```bash
# 杀掉广州一台节点（域内 3 节点剩 2，多数派还在，集群应继续可读写）
ssh root@110.41.85.62 "pkill -f 'node c2 '"
./scripts/cloud-client.sh a write 5          # 应正常

# 杀掉整个 GL 所在域（触发全局重选，另两域 ≈ 阈值 2 个 Domain Leader，能选出新 GL）
ssh root@1.92.115.7 "pkill -f 'cdraft-linux -config'"
sleep 15 && ./scripts/cloud-client.sh gl     # GL 应已迁到上海或广州

# 把北京拉回来（作为 follower 重新加入）
./scripts/cloud-deploy.sh start
```

数据持久化在每台机器 `/opt/cd-raft/data/<节点id>/`（内嵌 LevelDB），重启进程自动恢复，不丢已提交数据。

## 八、自动迁移（可选）

节点会统计各域读写负载和跨域 RTT；外部控制器 `cdraft-mover` 轮询统计、跑代价模型、通过安全交接把 GL 迁到负载最优的域。在本地直接跑（它通过 EIP 访问所有节点）：

```bash
go build -o bin/cdraft-mover ./cmd/cdraft-mover
./bin/cdraft-mover -config config/cluster.huawei.json \
  -poll 2s -confirmations 2 -cooldown 8s -min-improvement 0.1
```

然后从某个非 GL 域持续打负载（如 `./scripts/cloud-client.sh c write 200`），观察 mover 日志把 GL 迁过去，再用 `./scripts/cloud-client.sh gl` 确认。

### 手动指定 GL 域

要把 GL **强制**迁到指定共识域（不靠负载/代价模型），用 `cloud-gl.sh`（本机走 EIP，内部调 GL-only 的 Move RPC 做安全交接，不停节点、无停机）：

```bash
./scripts/cloud-gl.sh show       # 当前 Global Leader 节点 + 域
./scripts/cloud-gl.sh move c     # 安全交接到 domain-c（广州）
```

首次运行会自动构建 `bin/cdraft-client`。前提同 mover：各域 EIP 的客户端端口（默认 7101）对本机可达。
