# 快速部署测试

一份从零到出结果的「照抄即可」指南:**设置跨域延迟 → 启动集群 → (可选)指定 Global Leader 所在域 → 启动 client 跑读写**。

所有命令都在 `docker/` 目录下执行:

```bash
cd docker
```

只用到 4 个脚本,各管一件事:

| 脚本 | 作用 | 是否重启容器 |
|------|------|--------------|
| `./cluster.sh` | 构建/起/停集群、看状态 | 是(`build`/`up`/`staged`/`down`) |
| `./latency.sh` | 在线改跨域延迟(`tc`) | 否(热更新) |
| `./gl.sh` | 看/指定 Global Leader 在哪个域 | 是(`move` 会停启一个域) |
| `./client.sh` | 从某个域发读/写,逐条打印延迟 | 否 |

> 默认延迟矩阵(单向 ms):`a<->b 50`、`a<->c 80`、`b<->c 60`(RTT 为其两倍:100 / 160 / 120 ms;同域 ~0)。

---

## 零、改完代码后如何生效(必看)

`cdraft` / `cdraft-client` 的二进制是 **编译进镜像** 的(不是挂载源码),所以在宿主机上改完 Go 代码后,**光 `restart` 不会生效**——必须重新编译镜像并重建容器。9 个节点 + client 共用同一个 `cd-raft:local` 镜像(只由 `a1` 服务声明 build),所以**只需 build 一次**,所有容器都会更新。

```bash
cd docker

# 方式 A:一条命令重建并全量重启(最常用)
./cluster.sh up            # = docker compose build + up -d(--build 重建镜像后重建所有容器)

# 方式 B:先单独编译镜像,再决定怎么起
./cluster.sh build         # 仅重新编译 + 重烤镜像(= docker compose build)
./cluster.sh up            # 用新镜像重建全部容器
#   或
./cluster.sh staged        # staged 会先 build,再 down -v 清库,然后逐域启动(干净重测)
```

> - 改了**业务代码**(`internal/cdraft`、`cmd/...`)→ 必须 `build`(方式 A 或 B)。
> - 只改了 `cluster.docker.json`(拓扑/特性开关,是只读挂载的)→ 不用 build,`docker compose up -d` 重启即可。
> - 改了持久化格式(如本次 JSON→LevelDB)→ 旧 volume 里是旧格式数据,建议 `./cluster.sh down -v` 或用 `staged`(自带 `down -v`)从干净状态开始,避免新旧数据混淆。
>
> 底层等价命令:`docker compose build`(编译)+ `docker compose up -d --force-recreate`(用新镜像重建容器)。

验证容器确实跑的是新镜像(对比镜像构建时间 / 镜像 ID):

```bash
docker images cd-raft:local                       # CREATED 应是刚刚
docker compose ps                                  # 各容器 IMAGE 均为 cd-raft:local
```

## 一、最短路径(默认延迟,5 步出结果)

```bash
cd docker

# 1. 构建镜像 + 启动全部 9 节点 + client
./cluster.sh up

# 2. 等约 8s 选主,确认就绪(GL 出现即可)
./cluster.sh gl
./cluster.sh status        # 9 个节点应收敛到同一个 GL、同一个 gTerm

# 3. 从某个域写 10 次、读 10 次(逐条打印延迟)
./client.sh a write 10
./client.sh a read 10
```

就这样。下面是可选的「调延迟」和「指定 GL 域」。

## 二、设置跨域延迟(可选)

`latency.sh` 用 `tc` **在线**改延迟,不重启容器、不重建镜像,改完立即生效。

```bash
./latency.sh show              # 看当前每个域的 egress 整形
./latency.sh set 50 80 60      # abc 矩阵 + 默认 d 链路
./latency.sh set 50 80 60 120 25 90  # 完整矩阵:ab ac bc ad bd cd(单向 ms)
./latency.sh pair a c 120      # 只改 a<->c 这一条 → 单向 120ms(RTT 240ms),其余不变
./latency.sh pair b d 40       # 只改 b<->d 漂流域链路
./latency.sh reset             # 恢复默认 50/80/60/120/25/90
```

验证延迟真的生效(实测内核级延迟,ICMP 即可,RTT = 两侧单向之和):

```bash
docker compose exec a1 ping -c 3 10.10.3.11   # a<->c
docker compose exec b1 ping -c 3 10.10.3.11   # b<->c
docker compose exec client-d ping -c 3 10.10.2.11 # d<->b
```

## 三、指定 Global Leader 所在域(可选)

全局选举是对称随机的(没有「优先域」开关)。`gl.sh move` 通过「**驱逐当前持有 GL 的域 → 剩余两域重选 → 把被驱逐的域拉回来当 follower**」的方式,把 GL 收敛到你指定的域(目标域始终不被停)。

```bash
./gl.sh show        # 当前 GL 是哪个节点 / 哪个域
./gl.sh move a      # 把 GL 强制移到 domain-a(几轮内收敛,结束时所有域都在跑)
```

> ⚠️ **顺序很重要**:`gl.sh move` 会 `stop/start` 被驱逐的域,该域重跑 entrypoint → **tc 延迟被重置成默认矩阵**。
> 所以若要「自定义延迟 + 指定 GL 域」一起用,**先 `gl.sh move`,再 `latency.sh`**。

## 四、启动 client 跑读写

```bash
# 用法:./client.sh <a|b|c|d> <read|write> [条数] [key] [value]
./client.sh a write 10          # 从 domain-a 写 10 次(默认 key=foo value=bar)
./client.sh a read 10           # 从 domain-a 读 10 次
./client.sh b write 10 k v      # 从 domain-b 写 10 次 k=v
./client.sh c read 5 k          # 从 domain-c 读 5 次 key=k
./client.sh d write 10          # 从漂流域 domain-d 写 10 次
./client.sh d read 10           # 从漂流域 domain-d 读 10 次
```

`client.sh` 会自动 exec 进该域的首节点(`a1`/`b1`/`c1`)；漂流域 `d` 会 exec 进 `client-d`，它没有 CD-Raft 节点，只作为 `origin-domain=domain-d` 和 Fast Return reply-route 存在。请求从域内发出,走真实 tc 整形的 client↔GL 链路；对 `d write`，脚本会后台启动 discovery/probe/report，不阻塞前台请求。冷启动先走 GL normal RPC，遥测收敛后后续写再自然进入 responder race。它自动填好 `-target / -origin-domain / -reply-route / -callback-listen`,逐条打印每次延迟,并给出 `total / avg / min / max` 汇总。

默认矩阵里 `d` 离 domain-b 最近，所以 `d` 会先从 b1 这个最近入口 bootstrap，再跟随当前 GL redirect。

输出示例:

```
[1/10] write winner=domain-leader-fast-return index=2 result=foo=bar latency=166ms
[2/10] write winner=domain-leader-fast-return index=3 result=foo=bar latency=165ms
...
----
ops=10 success=10 failures=0 total=1.99s avg=199ms min=164ms max=494ms
```

## 五、完整示例:自定义延迟 + 指定 GL + 三域读写

把 GL 钉在 domain-a,把 a<->c 调成 200ms RTT,然后从三个域分别测:

```bash
cd docker

./cluster.sh up                 # 起集群
./gl.sh move a                  # 先指定 GL 域(会重置被动域的 tc)
./latency.sh set 50 100 60      # 再设延迟:ab=50 ac=100 bc=60,d 链路用默认值
./latency.sh show               # 确认

# 三个域各 10 写 + 10 读
for d in a b c; do
  echo "######## domain-$d ########"
  ./client.sh $d write 10
  ./client.sh $d read 10
done
```

## 六、怎么解读结果

第 1 条总是偏高(冷连接握手 + 首次重定向发现 GL);**客户端会缓存 GL 地址,从第 2 条起是稳态**,每个请求只付一个 client↔GL 往返。

**读**:只由 Global Leader 在读屏障后服务,稳态延迟 ≈ 一个 client↔GL RTT。

| client 所在域 与 GL 所在域 | 稳态读延迟 |
|----------------------------|------------|
| 同域 | ~0.1 ms(亚毫秒) |
| 跨域 | ≈ 该链路 RTT(如 a↔c=160ms → ~162ms) |

**写**:`winner` 字段说明谁应答的:

- `domain-leader-fast-return`:起源域 ≠ GL 域,起源域 DL 在拿到日志后快速应答 ≈ **1 个 client↔GL RTT**。
- `global-leader`:起源域 = GL 域,无快速返回,需等**完整两域提交**(GL→最近的第二个域的 RTT)。

> 例:GL 在 domain-c 时,从 c 域写(`global-leader`)≈ c↔b RTT(120ms);从 a 域写(Fast Return)≈ a↔c RTT(160ms)。**离 GL 越近、且第二近的域也近,写越快。**

## 七、看状态 / 清理

> 持久化已全部落到每个节点的**内嵌 LevelDB**(`/var/lib/cd-raft/<节点>/`):Raft 元数据、
> 日志(`log:<index>`)、应用状态机(`sm:<key>`)都在一个库里原子批量写入。运行中的节点会
> **独占锁住该 LevelDB**,所以**不能再 `cat` 状态文件**——要通过 gRPC 向存活节点查询。
> `cluster.sh status` / `cluster.sh gl` 已经改成走 `cdraft-client -status`。

```bash
./cluster.sh status     # 每个节点的 domainLeader / GL / gTerm / commit / applied
./cluster.sh gl         # 只看当前 Global Leader
./cluster.sh logs c2    # 跟某节点日志
./cluster.sh down       # 停掉并清空所有状态(-v)

# 也可直接查单个节点(在该节点内、用它自己的域内 IP,因为监听绑的是域 IP 而非 localhost):
docker compose exec -T b1 cdraft-client -status -target 10.10.2.11:7101
```

## 八、逐域启动(观察选举过程,可选)

想观察「一个域、两个域、三个域」时选举如何演进:

```bash
./cluster.sh staged     # 依次起 a → b → c,每阶段打印一次状态
```

- 只有 1 个域时:该域选出 Domain Leader,但**还没有 Global Leader**(全局选举需 `N-1=2` 个域),`gTerm` 不动。
- 起到 2 个域:达到阈值,跨域选出 Global Leader。
- 起到 3 个域:第三个域加入并跟随已有的 GL,九节点收敛到同一个 GL 和 `gTerm`。

> 更底层的原理、原始 `docker compose` 命令、tc 矩阵细节见同目录 `README.md`。
